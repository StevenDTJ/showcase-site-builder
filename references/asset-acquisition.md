# 图片资产获取规范（Midjourney 浏览器自动化）

图像资产获取的**唯一路线**：驱动受控浏览器在 Midjourney 网页端自动生产。不爬取第三方网站，不走"交付提示词等人工回填"的中转——提示词写出来就直接投喂、回收、校验。

逐项登记到资产台账：用途 / 提示词 / job 链接或 ID / 本地路径 / 状态（待生成 / 已回收 / 已验收）。

## 自动化闭环（机制与坑位，均为实测）

参考实现：[templates/mj-browser-automation.py](../templates/mj-browser-automation.py)——**机制以这段代码为准**；下面是它对应的规范。模板是通用壳：端口/profile/Chrome 路径走 `MJ_PORT` / `MJ_PROFILE` / `MJ_CHROME`，提示词清单走 `--prompts`（惰性加载，不在 import 时读盘）。

1. **受控浏览器**：系统 Chrome + `--remote-debugging-port` + 独立持久化 `--user-data-dir`（不动用户日常浏览器）。首次让用户在该窗口登录一次，会话长期保持；之后的运行全自动化。
2. **可信输入与提交**：React 受控组件不认合成事件——用 CDP `Input.insertText` 写入提示词，再用**完整 Enter 序列**提交：`keyDown`（**必须带 `text="\r"`**）+ `keyUp`；不生效时退到兜底序列 `rawKeyDown` + `char` + `keyUp`。
   **⚠️ 绝对不要「找一个按钮点下去」**：当前作曲框里**没有发送按钮**（只有 Add Images 与设置按钮），误点会打开文件选择器/设置面板并抢走焦点，之后 Enter 也不再生效——那是一条会**加剧故障**的歧路，不是备用方案。
   **提交成功的判据是双判据**（输入框被清空 **或** 页面出现本次之前没有的 jobid）。只认前者的话，一旦 MJ 清空得比轮询间隔慢，就会补发第二次回车——同一条提示词被提交两遍，白烧订阅的 fast hours。两档都失败就**硬清空输入框**（CDP 全选 + 删除）并如实报错，绝不把残留文字留在框里：下一次 `insertText` 会拼接到旧文字后面，生成一条根本没写过的提示词。
   需要更本质的证据时用模板的 `probe` 子命令：读 **Network 域**直接看有没有真的发出提交请求。「输入框清空了」只是间接证据（空框同样返回空串，会误判成提交成功）。
3. **结果识别：用 jobid 认领新任务，不要用提示词文本匹配**。任务身份是缩略图 URL 里的 `cdn.midjourney.com/<jobid>/0_N_640_N.webp` 中的 jobid。
   **为什么文本匹配在本 skill 下必然失效**：规范要求每条提示词共享同一段风格锚点（SA）开头，而卡片文本会被截断——主体短语根本不出现在 DOM 里，共享前缀又毫无区分度。按文本前缀匹配会系统性抓到别的任务的旧图。jobid 认领与文本长度无关。
   两个必须保留的纪律：
   - **跨任务累积「见过的 jobid」**：feed 会虚拟化，老卡片可能先消失再出现；只比对本次快照的话，重新出现的旧卡片会被误判成新任务（实测据此把某任务的图错收成另一任务的）；
   - **新任务永远插在 feed 顶部**，优先取 DOM 顺序里的第一张卡；
   - 认领到 jobid 后等它出齐 4 张。
4. **下载**：CDN 对裸 urllib 返回 403——在页面上下文里 `fetch`（带会话）→ base64 回传；全尺寸 `0_N.png` 间歇 403 属常态（延迟就绪），退避重试有效；再三试不过才退到 640px 预览图兜底。**降级必须留痕**（`full` / `preview` 随文件记录），台账注明——预览图只够选图，进页面或进 FLF2V 前必须补拉全尺寸。另一处静默陷阱：由缩略图 URL 推全尺寸时**必须按模式剥掉 `_640_N`**（`re.sub(r"_\d+_[A-Za-z]+\.webp$", ".png", u)`）；写成近似替换会得到 `0_1_640_N.png`——**那个文件是 640 预览，不是全尺寸**，而且能正常下载，不会报错。实测每批 4 张候选中可能有 1 张只回收到预览图；影响使用时修订提示词重投，而不是带病使用。
5. **副作用须知**：网页自动化游走在 MJ 服务条款边缘，首次使用前告知用户；生成消耗订阅 fast hours；账号的 personalization/moodboard 会改变成图风格（空泛提示词会被拉向账号口味）——资产生产用完整、具体的提示词可抵消。

## 风格校准（正式开跑前的第一步）：三种参考方向让用户选

一个站点的**风格锚点（SA）一旦批量开跑就很难回头**：全片提示词共享同一段 SA，风格定错了要全部重投、全部重挑。所以在写全量提示词之前，**先用同一个替身画面跑三种方向，让用户选一个**。

机制（实测有效的做法）：

1. **共用一个替身画面**：挑一个最能代表全片的画面（例如 hero 那个镜头），三个变体都画**同一个主体、同一个构图**，画幅一致——**只让"媒介 + 空间"这一个变量变化**；
2. **只换媒介从句，主体与构图逐字相同**：三条共享同一段主体描写（形状、材质、颜色、线索物）与同一段构图/调色约束（留白区、明度方向、配色），差异只在媒介与空间；
3. **每条提示词以各自的媒介词开头**：既让媒介权重最高，也让每条有一个天然唯一的短语（三条共享主体句，用主体句当标识会互相混淆）；
4. **各自的 seed 分开**（如 5101/5201/5301）：换 seed 才是真正换采样，共用 seed 会让 MJ 给出相近构图；
5. **产出对照图**：每个变体出 4 张，先各自拼一张 2×2 自评，再拼一张"三行并排"的横向对照图（每行一个方向、取前两张），**一行一方向**便于用户横向比较；
6. **停下等用户选**（A/B/C），选定后才把它写成全片的 SA、开始写全量提示词。**这一轮必须同时把配色方案与视觉基调交给用户拍板**（SKILL.md §1b）：三条方向各自带着一套候选色板与明度策略（同一替身画面、同一构图），用户既选媒介也选色——**不要自己先把色调定了再补问**。**对照物就是这三条方向的真实出图；不要为了对比再搭 HTML/CSS mock 页面**（会引入版式/字体这层额外变量，见 §1b 末条）。选定结果（方向 + 色板 + 时间）记进 `docs/art-direction.md`。

**典型三方向**（照抄实测有效的组合）：

| 方向 | 媒介锚点 | 空间 |
|---|---|---|
| A | `neoclassical oil painting, luminous high-key, restrained visible brushwork` | limbo（无缝浅底、无墙无窗无地平线） |
| B | `studio still life photograph, huge softbox, shadowless even light, medium format` | limbo |
| C | `copperplate engraving with fine crosshatching, eighteenth century book illustration plate` | 象牙色手工纸 |

**踩过的坑**：第一版把方向写成「18 世纪排字工坊室内、白灰泥墙、漂白橡木案」，那不是 limbo——**把工坊调亮也变不成 limbo**，那是"换了个房间"而不是"换成悬空主体"。做风格对照时，空间属性必须和媒介属性一起当变量考虑。

执行方式（两条路都行；不想污染主上下文就派子代理）。**注意参考实现不在本 skill 里**——`mj_calib.py` 是项目自己的、绑定了那部片的三个变体；新项目要么照它的结构写一份，要么直接用模板的通用壳：

```bash
# 项目自有实现（若该工作区里存在）：跑三个变体并拼 sheet_<id>.png + compare.png
python tools/mj_calib.py            # 跑三条并拼对比图
python tools/mj_calib.py --sheets   # 只重拼对比图
# 通用壳：--text 免清单投喂，三条各投一次；--labels 让徽章显示方向号而不是 0/1/2
python mj-browser-automation.py run --text "<变体A 提示词>" --id calA --out docs/qa/calib
python mj-browser-automation.py run --text "<变体B 提示词>" --id calB --out docs/qa/calib
python mj-browser-automation.py run --text "<变体C 提示词>" --id calC --out docs/qa/calib
python mj-browser-automation.py sheets --ids calA,calB,calC --out docs/qa/calib --labels A,B,C
```

⚠️ **别让"候选编号"和"方向标号"混起来**：正式生成时每组 4 张用 0–3（文件名下标）；校准对照用 A/B/C/D。两者都是编号，交付给用户务必说清是哪一组。

## 提示词规范

### 结构

```
[主体与动作], [媒介质感], [光线], [色调], [构图/镜头], [氛围] --ar 比例 --style raw
```

常用质感关键词：

- 油画：`oil on canvas, Dutch Golden Age still life, chiaroscuro, visible craquelure`
- 版画/雕刻：`copperplate engraving, fine crosshatching, 18th century book illustration`
- 静物摄影：`studio still life, single soft key light, dark linen backdrop, medium format`

### 构图与留白（进入页面的图都必须遵守）

图片不是独立艺术品，是**文字的布景**。留白是指定的设计参数，不是生成后的剩余：

1. **平静区在提示词里点名**：明确写出哪个区域要低信息密度（`left third: plain plaster wall, no objects` / `upper right falls into deep empty shadow`），不要生成后再找空地；
2. **主体避开正中央**：居中主体会同时挡住左右两个文字位——放在井字格交点；文字位在分镜脚本阶段就标注（左上/右下…），各帧左右交替形成版面节奏；
3. **明度分区**：文字落位区整体暗（配亮字）或整体亮（配暗字），忌高频细节（密花纹墙纸、密集树叶）。复杂画面风格（如满室油画）做"指定平静区"，不强求 limbo 空背景；
4. **overscan**：页面用 `object-fit: cover` 会裁切四边，关键主体离画面边缘 ≥10%；
5. **帧图的多重身份**：首帧可能同时用作视频 poster、降级模式静态图、社交分享图——必须能脱离视频独立成立；
6. **线索物固定描写句**：贯穿全片的线索物（见 film-language.md）写一段不变的描述（形状、材质、颜色），逐帧复用，逐帧只改叙事要素。

### 首尾帧配对（FLF2V 用）

**核心约束：Midjourney 无法稳定复现同一场景的构图、机位与光线。** 因此放弃"同一场景不同状态"的配对思路——每张参考帧设计为**不同的主体或场景**，帧间的转化交给视频模型完成：

- **段内（首帧→尾帧）是两个不同画面**：例如"满树梨"→"切开的梨递出"、"建筑工地"→"纸面蓝图"。首帧到尾帧的具体变化过程由视频提示词显式描述（见 comfy-flf-video.md 第三步，用 h3-json-director skill 撰写）。
- **跨帧一致性靠锚点，不靠场景复制**：两帧共享同一段风格锚点文字（媒介质感、光线方向、色调）、线索物固定描写句、画幅 `--ar`——这是允许场景完全不同的前提下保持"同一部影片"的手段。
- **段间（A 段尾帧 → B 段首帧）靠文件复用焊接**：相邻两段共享的边界帧是**同一张图片文件**，绝不分别生成两张"相似"的图。分镜阶段就标出哪些帧是共享帧，共享帧只生成一次。
- 每帧仍是独立成立的画面（可能用作 poster / 降级静态图），遵守上面的构图与留白规范。

## 候选挑定（每组回收后的第二步）：四张标号让用户选

四个候选都回收全尺寸之后**不要替用户选，也不要只用文件名报图**——把每组拼成一张带**大号编号徽章**的 2×2 对比图（编号 **0–3**，即文件名的下标 `_0`…`_3`），用户就能用一句话指认（"fh 要 2、f3 要 0"）。

规矩：

1. **编号必须稳定且可复述**：徽章上的号 = 文件名里的下标。不要出现"左起第二张"这类依赖排版的说法；
2. 徽章上同时标出**全尺寸 / 预览(640)**：回收时降级成预览图的候选必须让用户看得见——读者能接受"这张构图对但只有预览，稍后补拉"，但不能接受事后才发现；
3. **一次交付**（整批 16 组一起给）通常优于逐组打断；用户也可以逐组回。编号体系不变，两种节奏都成立；
4. **用户挑定后先落盘再动手**：把选择写进 `docs/qa/picks.json`，再按它收档，别凭记忆操作。

`picks.json` 格式（实测用过）：

```json
{
  "_format": "值 = 候选编号 0-3；\"root:<文件名>\" = 采用工作区根目录下的外部文件",
  "picks": { "fh": "root:0_2.png", "f1": 0, "f2": 3 },
  "roles": { "film": ["fh","f1"], "plate": ["p1"], "loop_poster": { "fh": "loop-hero-poster.jpg" } }
}
```

- **两组编号不要混**：上面是"每张图的候选号"，下面校准用的是"风格方向号（A/B/C）"，两者都是编号，交付给用户时要说清是哪一组；
- `picks.json` 只记录**决定**，不记录处理结果——收档（定稿原图进 `assets/src/`、页面用 WebP、循环段 poster 落到 `assets/video/`）是下一步按它执行的动作；
- **允许用户绕过候选**：他可能自己到 Midjourney 网页上重出一张（MJ 的 Remix / Vary 在批量场景下不可控），存成工作区根目录的文件后，用 `"root:<文件名>"` 采用。这是合法路径——**先核对它与已有候选不重复（sha1）**，再登记。

## 验收

- 回收后逐张用 `read_image` 检查：主体、机位、光线、平静区位置是否与脚本/提示词一致；不符合就修订提示词重新投喂，不要把错配的资产带进后续流程；
- 帧对检查：目检首帧与尾帧之间是否存在可读的转化路径（推近细节、线索物延续、明度/色温衔接）——完全不同的两张图不等于可插值，突变过大视频会崩坏；段间共享帧确认两段工作流引用同一文件；
- 每条资产回写台账（用途、提示词、job ID、路径、状态）。
